# Troubleshooting

Real failure modes, in rough order of how often they bite. Every one of these has
actually happened.

## The install printed FAIL at step 8b

**Read it. It is no longer the race it used to be.**

Step 8 enables Identity-Aware Proxy on the console and removes the public invoker
binding. Step 8b used to probe the console seconds later, **once, with no backoff**,
and IAP enforcement propagates asynchronously at Google's edge -- so on a fast machine
that single probe read a `200` from a console that was about to be guarded and
reported a false `FAIL FN.CONSOLE_IAP`. That probe now retries with backoff to a
deadline and **exits the instant** it sees an IAP-shaped refusal, so a guarded console
is never slower than one probe and an unguarded one still fails. The line it prints
says how long it waited and across how many attempts.

Step 10 re-measures the same property later, and a pass there **retires the 8b finding
by name** and prints the retirement. The closing summary names every failure it counts,
including inherited ones, so a count with no matching line above it cannot happen.

**How to tell for yourself, which is the only answer that should satisfy you.** Read
the *headers*, not just the status code -- the status code alone cannot answer this
question, and that is the single most important thing on this page:

```
curl -sS -o /dev/null -D - https://<your-console-host>/harness \
  | grep -iE '^(HTTP/|x-goog-iap-generated-response)'
```

Four outcomes, and only one of them is the console you want:

- **`401` (or `302`) *with* `x-goog-iap-generated-response`.** The refusal was
  generated by IAP at Google's edge, before your container was reached. That is a
  guarded console. This header is set by IAP and by nothing else, which is why step 8b
  asserts on its presence rather than on the code -- read the probe in `oss/gen.py`
  if you want to check that claim rather than take it.
- **`401` *without* that header, serving the locked page.** That refusal came from the
  application's own session check, not from the edge. It is not nothing -- an
  anonymous caller still got no data -- but it is one layer where the design calls for
  two, and step 8b records it as a **FAIL** for exactly that reason. The status code on
  its own would have passed, which is why the status code on its own is not the check.
- **`200` with console HTML.** The failure is real. Fix it before doing anything else.
- **Nothing at all, or a connection error.** You have the wrong host. See below.

**What you will not see any more, and should not go looking for: a redirect to
`/gate`.** That route, the 142,608-byte document behind it, and all ten redirects into
it were deleted on 2026-08-14. Every site that used to bounce you now serves
`control-plane/src/locked.html` **in place**, under a `401`, at the URL you actually
asked for -- no redirect, no `?next=`. Unlocking reloads you where you already were.
`GET /gate`, `GET /jobs` and `GET /pastes` return `404` (measured against a running
build). The one `302` that remains is `GET /` to `/harness`, which is a bare
unconditional redirect that reads nothing and issues no session.

That change also removed a way for this check to lie to you. A `302` used to look like
guardedness to a script and like a working page to a human, and the installer's own
guard check read one as proof the console was protected. A `401` means *refused*, and
it says so to both readers. No `WWW-Authenticate` header is sent, so no browser
credential dialog appears.

A check that races the thing it measures is wrong in both directions, and waiting
longer on an open console makes the FAIL arrive later rather than turning it into a
pass. A false **green** would have been much worse.

## The agent client cannot connect

Almost always the URL.

**Use the MCP service host, not the console host, and include the path:**

```
https://<your-mcp-service-host>/mcp
```

The console is behind IAP. IAP consumes the `Authorization` header, and an MCP client
has no Google identity to present, so `POST /mcp` against the console is refused at
Google's edge before your container is reached. There is no fix at the application
level -- IAP on Cloud Run is one switch per service with no path-level carve-out.
That is exactly why there are two services.

Second most common: the bare host with no `/mcp` path. Third: the placeholder URL in
`agent-plugin/mcp.json`, which ships unresolved on purpose because your hostname does
not exist until you install. Use the resolved copy the installer wrote beside it.

Recover the right host:

```
gcloud run services describe <mcp-service> \
  --region <your-region> --project <your-project> \
  --format 'value(status.url)'
```

## Chat returns 403, or every model fails at once

The control plane's service account is missing Vertex access.

```
gcloud projects add-iam-policy-binding <your-project> \
  --member serviceAccount:<control-plane-service-account> \
  --role roles/aiplatform.user
```

Both providers default to Vertex, so a missing `aiplatform.user` takes out Claude and
Gemini together. If only one provider fails, it is not this -- it is model
enablement or a region mismatch. See **Model configuration**.

The error body now carries the host, transport, region, model, HTTP status and the
upstream message verbatim, with keys and bearer tokens stripped. Read it; it usually
names the problem outright.

## Claude chat returns 404, and the key you set made no difference

This one is worth reading slowly, because the obvious diagnosis is the wrong one.

**`CHAT_CLAUDE_PROVIDER` defaults to `vertex`, and a key cannot change that.** Only
`anthropic`, `api`, `key` or `direct` leave Vertex; anything else, **including unset**,
means Vertex. An `ANTHROPIC_API_KEY` on the service, or a `chat-key-claude` version in
Secret Manager, is **data, not configuration** -- it is not consulted when choosing the
transport and it will not be sent to Vertex. So "I set a key and it still fails" is not
a contradiction; the key was never in the path.

**On Vertex the model id is part of the URL, and it must be a Vertex publisher id.**
MEASURED in `control-plane/src/index.ts`: the Vertex request is built as
`.../publishers/anthropic/models/<model>:rawPredict` with the configured id
interpolated verbatim into the path, the `model` field deleted from the body, and
`anthropic_version` added. A Vertex publisher model id is **not guaranteed to be the
same string** as the model name the Anthropic API answers to, and when it is not,
Vertex returns `404` for a publisher model it does not have under that name -- however
correct your credentials are. **Model configuration** records the measured version of
this trap on the Gemini side: the configured Gemini id is a Vertex publisher id, it
does not exist on AI Studio, and sending it there returns `404` no matter how valid the
key is. The Claude direction is the same mechanism read the other way round, and it is
the first thing to check when the transport is right and the request still 404s.

Two further ways to earn a `404` here, both region-shaped:

- The Claude region defaults to `us-east5` (`CHAT_VERTEX_REGION`, else
  `VERTEX_LOCATION`). It is **deliberately not** `GCP_REGION`, which is the Cloud Run
  region and defaults to `us-east1`, where Vertex serves no Anthropic model. If you
  "helpfully" aligned the two, that is your `404`.
- A publisher model has to be published in the region you are asking. Overriding the
  region without checking that gets you a `404` rather than a redirect to where it lives.

**Do not diagnose this from the code.** The console tells you what it actually chose:

- one `[chat/resolve]` line per request in Cloud Logging -- provider, transport, region,
  host, model, effort, and `key_present` as a **boolean**, never a value;
- `GET /api/keys/status`, which returns the same resolved view for both providers and
  is behind the console session like everything else.

If that says `transport: vertex` while you believed you were on the direct API, you have
found it. To actually move, set the variable and redeploy -- see **Model configuration**
-- and then re-read `/api/keys/status` rather than assuming.

## The wiki is empty, or a page 404s

**The installer seeds these pages at step 6b, and reports what landed.** An empty
wiki therefore means that step did not finish -- it prints the count it read back and
the exact copy commands to finish by hand. If you are reading this page, it worked.

**First, make sure you are signed in.** `/wiki` and `/wiki/<slug>` check the console
session before they touch the lake, and an anonymous caller gets `401` with the locked
page rendered at the URL they asked for -- not a redirect, and not any of the messages
below. The anonymous answer is byte-identical whatever slug you ask for, on purpose:
a response that varied with the slug would tell an unauthenticated caller which pages
exist. If you are looking at the lock, none of this table applies yet.

Signed in, the route reads every byte it serves from `shared/wiki/` in the lake:

| symptom | cause |
|---|---|
| locked page (401), any slug | no console session -- the check runs before the lake is read |
| "The wiki is empty" (HTTP 200) | `_index.json` absent, or its `pages` array is empty |
| "No such page" (404) | slug not listed in `_index.json`, or it fails the slug shape rule |
| "Page listed in the index but absent from the lake" (404) | the index names a slug whose `.md` object is missing |
| "Wiki shell unavailable" (503) | `_shell.html` is missing |
| "Wiki store unavailable" (503) | the object store refused the read -- a real outage, not absence |

`_index.json` is the allow-list as well as the nav tree. **A page present but
unlisted is unreachable; a page listed but absent 404s.** Both checks run before any
path is joined.

## Every wiki page shows a red FRESHNESS UNKNOWN banner

The badge is RED whenever a page cannot prove it is current. Causes, in order:

- The page's `watch` list names something that does not resolve -- an object that is
  not there, or a watch kind this install cannot answer.
- The watch list is empty, or the front-matter is missing or unparseable.
- Front-matter `page:` does not equal the slug.
- The watched lake object was deleted.

RED is the correct answer to all of those. The badge will call itself unverified
rather than call itself current, and a store outage turns every page red because
during an outage the wiki genuinely cannot vouch for itself.

## A page renders as WITHHELD

The page body matched a credential pattern -- a session key or a bare bearer token --
and was not rendered. The match was logged.

Remove the value from the page object and **rotate whatever it named**. A credential
pasted into a document is a second permanent copy of that credential on a
human-readable surface. Deleting the page does not undo that.

## Re-running the installer over an old install fails on a secret

Step 6 deploys with `--update-secrets`, which adds and updates the keys it names but
does not remove a binding it does not name. A service left behind by an older
installer can keep a reference to a secret current versions neither create nor grant
access to, and the deploy is refused on a secret nothing reads.

```
gcloud run services update <mcp-service> \
  --remove-secrets=APPROVAL_MAC_KEY \
  --region <your-region> --project <your-project>
```

Or delete the service and let the installer recreate it.

**Do not fix this by granting access to that secret.** Approval integrity rests on an
asymmetric Cloud KMS signature. Handing a symmetric key back to a service that
verifies with a public one undoes the property that signature exists to provide: the
executor is fail-closed on an unsigned approval, and a symmetric key that both ends
hold is forgeable by either end.

## A staged job never runs

**First, the thing that changed on 2026-08-14: fewer jobs stop than used to.**
`PC_GUARDRAILS` defaults to `0` in both the control plane and the executor, and with it
off a destructive command and a lockout-class change **run**. They are still detected
and still journalled -- a lockout-class match that ran anyway is recorded under its own
action, `exec_lockout_class_ran`, so the transcript can answer "what took the console
out" without anyone guessing. The operator's ruling was that the person issuing the
instruction is the person who would be asked to confirm it, so the second question buys
nothing. `PC_GUARDRAILS=1` restores the refusals for an adopter who wants brakes.
Detection is not friction; a refusal is. Only the refusals went.

So if a job did not run, check, in this order:

1. Was it **staged** rather than run? Some tool paths still answer `{"mode":"staged"}`
   and stop. **The approval channel is now chat, not a page you tap** -- the gate
   console it used to point at is deleted, so a staged job waits on an answer in the
   conversation and comes back re-issued once you give one. The console's own fire
   endpoint requires a fresh elevation, and on a stock install (`PC_REQUIRE_PASSKEY=0`)
   no console page calls it.
2. Was it **refused** rather than pending? `read_job_log(job_id)` returns a reason.
   A refusal happens before the approval is consumed, so a refused job costs you
   nothing and the same approval can be presented again once the cause is fixed.
   With guardrails off, the refusals you are most likely to meet are the ones that
   run *before* a job exists -- a duplicate of something already staged, or a secret
   destroy that has not been through the consumer preflight.
3. Does the tool need something `install.sh` does not provision? `vm_*` needs a
   workstation, and the installer builds none -- run `workstation.sh`, then set
   `WS_VM`/`WS_ZONE` on both services. Browser tools additionally need a CDP endpoint the
   control plane can reach, which the loopback-only bridge is not.

## Nobody can get into the console

A fresh install sets `PC_REQUIRE_PASSKEY=0`, so what admits you is a **verified IAP
identity on the approver allow-list** (`WA_APPROVER_EMAILS`) and nothing else. If your
account is not on that list, or IAP will not admit it, you get the `401` and
`control-plane/src/locked.html` -- which on this posture is a dead end, because there is no
credential enrolled to unlock with.

It refuses rather than defaulting open, and there is no path around that from inside the
console itself. The escape is a deploy-time change to `WA_APPROVER_EMAILS` (or to the IAP
binding), and either needs `run.admin` / IAM rights -- which the control plane's own
service account deliberately does not hold. That is the point: a compromised control plane
cannot unlock itself.

The WebAuthn unlock did **not** go away with the gate. It lost the larger of its two
documents and kept the small one, and `PC_REQUIRE_PASSKEY=1` puts it back in the path --
which is the way back in if the identity provider in front of the console ever fails. The
operator's guide has that switch.

Prevent it: **keep at least two accounts able to reach the console**, on the IAP binding
and on `WA_APPROVER_EMAILS`. Do it now, not after you have lost the first. Make the second
one **in-domain**, because the domain-restriction constraint that makes an out-of-domain
grant impossible also means a stranger's account cannot rescue you.

## The deploy said it succeeded and the old code is still serving

A deploy reporting success and a revision actually serving traffic are two different
facts, and here they come apart for a specific, repeatable reason: **traffic is pinned
by revision name.** A new revision can build, deploy, pass its health check and sit at
zero percent while the revision you were trying to replace keeps answering every
request. Nothing errors. The logs look healthy. They are the *old* revision's logs.

Worse, **`gcloud` misreports which revision it deployed.** Do not trust the revision
name it prints. Ask the service what is actually serving:

```
gcloud run services describe <console-service> \
  --region <your-region> --project <your-project> \
  --format 'value(status.traffic.filter("percent:100").revisionName)'
```

and compare it against what the deploy really created:

```
gcloud run services describe <console-service> \
  --region <your-region> --project <your-project> \
  --format 'value(status.latestCreatedRevisionName)'
```

If those two differ, that is your answer, and re-pinning traffic is the fix:

```
gcloud run services update-traffic <console-service> \
  --region <your-region> --project <your-project> \
  --to-revisions <revision>=100
```

**Read `status.latestCreatedRevisionName` back at the moment of the deploy, not
later.** Re-deriving "the latest revision" afterwards and assuming it is the same one
is how you verify one revision and promote another -- a concurrent deploy between the
two reads makes them different revisions. `deploy/BUILD-FROM-THE-STORE.md` records this
step and it is the one most often skipped; skipping it is what produces the "I deployed
the fix and nothing changed" report.

If the serving revision *is* the one you just built and the behaviour still did not
change: confirm the file you edited is one that ships -- see **Changing the code**, and
note in particular that `control-plane/Dockerfile` does not run `npm run build`, so
editing the `package.json` build script compiles nothing. If you changed an environment
variable, confirm you set it on the right service: MCP tool configuration on the MCP
service, console configuration on the console. An environment change needs a redeploy
of the affected service; a source change needs a rebuild.

## An agent described code that does not exist

Take this seriously the first time it happens, because the failure is confident and
detailed rather than obviously broken. **The two plaintext mirrors are dead.**
`gs://<lake>/shared/repo/HEAD/` and `gs://<project>-source/<repo>.git` are both
**stale** and neither is a source of truth. Agents read them *as* the repository and
reported, in detail, on code that had not existed for weeks. This is a measured failure,
not a caution.

The tell: a description that is internally coherent, names real-looking files and line
numbers, and does not match what you see in the console or in a fresh checkout. If a
document, a job, or a helpful-sounding shell snippet you inherited reads either path,
that thing is out of date -- and so is anything derived from it.

The repository lives as refs in Firestore with its objects **PCV1-encrypted** in the
lake, which is the whole reason there is a procedure at all: no build system and no
agent can read those objects directly. There are exactly two supported reads.

**A machine** fetches `GET /git/archive` on the **MCP service host** -- not the console
-- presenting a Google-signed service-account ID token. It is audience-pinned and
allow-listed by `PC_ARCHIVE_ALLOWED_SA`, which **fails closed when unset**: unset means
*no* caller, never *any* caller. The response is a gzipped tarball carrying its own
manifest in headers (`x-pcgit-commit`, `x-pcgit-files`, `x-pcgit-bytes`), so a build
step can assert coverage rather than trust a byte count.

Every refusal on that route answers the same flat `401 {"error":"unauthorized"}` --
unset allow-list, wrong audience, non-allow-listed service account and malformed token
are indistinguishable to the caller, deliberately. **The reason is written to the
service log**, so a `401` here is a question for Cloud Logging, not something to guess
at by permuting flags.

**A human, or a deploy** materialises a checkout through the store: fetch
`shared/deploy/lane-fetch.py` with a raw copy (it lives in a cleartext prefix), use it
to pull `<your-exporter-object>` **through the vault codec**, export
with `--expect-ref`, then clone. If you fetch the exporter with a plain
`gcloud storage cp` you get a PCV1 envelope and `python3` dies with `SyntaxError: source
code cannot contain null bytes`. Nothing is corrupt -- you used the wrong fetcher, and
it fails in the worst possible way because the copy itself looks healthy.
`deploy/BUILD-FROM-THE-STORE.md` is the long form.

## Nothing above matches

Errors in responses carry a correlation id (`err_id`) and nothing else. The full
exception goes to Cloud Logging, which is already access-controlled, so you lose
nothing by the response being terse:

```
gcloud logging read \
  'resource.type=cloud_run_revision AND textPayload:"<err_id>"' \
  --limit 20 --project <your-project>
```

Read the journal too. Every staged job, every lake write, and every strain action is
recorded with the role that did it. Since guardrails default off, the journal is also
where the *runs* that would once have been refusals show up -- `exec_lockout_class_ran`
for a lockout-class change that ran because `PC_GUARDRAILS` is off, and
`exec_lockout_acked` for one that ran on an explicit operator acknowledgement. If the
console went dark and nobody knows why, those two action names are the first thing to
search for; the record is what makes rolling forward possible.
